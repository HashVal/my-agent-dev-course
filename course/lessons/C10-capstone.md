# C10：综合验收与复盘

前九课留下了模型调用、结构化输出、工具、循环、检索、上下文选择、评测和错误处理。把这些文件放在一起不等于系统已经通过验收。另一个人需要知道从哪个命令开始、哪些代码必须由自己完成、用的是什么资料和配置、哪份记录支持“这个改动有效”。

本课解决：**怎样用可复查的证据解释系统的能力、失败和下一步？** 前置是已完成的核心 lab 与 C08 评分记录。你要演示一条完整任务，复跑一个小型比较，分析至少一个真实观察到的失败，并生成能够定位代码与记录的本地交接清单。

## 先确定到底交付什么

贯穿项目的目标仍然很小：在指定教学资料中查找依据，回答问题、注明来源，资料不足时说明缺口；程序记录行动并限制运行。课程没有要求生产部署、开放 shell、浏览外网或复杂多 Agent。综合验收首先检查这些承诺，而不是以新功能数量衡量完成程度。

一个可交接的结果至少连接四样东西：运行代码、复现命令、测试与评分记录、解释限制的说明。代码给出实现，命令说明如何启动，记录表明实际发生什么，解释告诉读者哪些结论有证据、哪些还不知道。

如果没有真实接口，可以交付模拟验证的程序与记录，但必须标为 `simulation_only`。这不是无效工作：消息配对、边界与预算都能得到程序证据；真实模型的工具选择和端到端效果仍没有被检查。不能为了结课把两种证据混成一份“全通过”。

## 沿完整链路解释一次任务

选择一个已经运行过的组合问题，例如 T01 是否达到工具上限。先指出原问题在哪里进入输入，再沿实际轨迹说明：模型提出什么调用，程序怎样验证参数，哪个文件被读出，结果怎样进入下一次请求，最后怎样结束与评分。

```text
问题与规则 → 上下文构造 → 模型请求 → 工具提议
                                  ↓
评分 ← 最终回答 ← 下一次请求 ← 校验、执行与反馈
                  ↑                  ↓
             上下文选择         次数与错误记录
```

这张图不要求每次都走相同文件顺序。它让你解释职责：模型决定提议什么，程序决定是否执行；运行器保存轨迹，评测器另行核查业务结果。C02 的 JSON 约定、C03 的权限和 C04 的循环在这里形成同一条路径，而不再只是互不相关的小例子。

如果下一次请求的消息里没有某个工具结果，就不能说模型已经据此作答；如果计数超过上限，答案碰巧正确也不能算程序边界通过。演示应展示能够核查这些判断的记录，而不只展示最后一段输出。

## 用基线限制自己的结论

全文基线和当前 Agent 用相同任务、资料与输出契约运行，才便于解释复杂度的价值。C08 的十题记录应保留通过、失败与实际成本指标。若 Agent 没有改善结果，却增加调用，最合理的下一步可能是保留全文或固定流程。

有时 Agent 在 A17 这类需要追踪代号的任务上更好，却在简单上限问题上更慢。可以据此提出按任务分流的假设，但不要直接宣称已经实现或验证。先写清触发条件，下一轮只比较这个改动，才知道差异来自哪里。

小样本只支持对这组任务和配置的诊断。“十题全对”不等于任意资料都可靠；“这次更快”不等于稳定低延迟；“路径测试通过”不等于完整沙箱。把限制写清楚是为了让别人能够正确使用结果，不是为失败找理由。

## 失败分析怎样成为可验证的解释

下面是一个虚构分析方式，不能复制成个人实践证据。现象：系统回答 A17 额度为 3 次。检查请求发现模型只收到了通用规则，没有 A17 与 QH-Z9 的关系。当前证据支持“必要资料没有进入该次请求”，还不能确定是检索没命中、排名截断还是消息组装丢失。

下一步依次查看检索结果和实际发送内容：若结果里已有映射但请求没有，应该修组装；若映射在第四条而 top-3 截掉了，才考虑检索与选择策略。提出一个单变量改动，再对原失败及保留案例检查。不要同时改模型、提示词、检索和预算，最后只报告“好了”。

分析包含六项：观察到的现象、原因证据、仍待验证的假设、具体改动、验证结果、剩余限制。未做改动时写“未修改”及理由；没有预算复测时写“尚未验证”，保留未完成状态。不能在清单中填一个“通过”代替记录。

## 复现不是自动重放一切

运行说明要写清 Python 版本、课程代码与本地实现版本、使用哪个模型标识、哪些环境变量需要在终端设置、每个命令最多几次请求、资料来源和日志位置。不要把密钥值写进说明或提交记录。

本课工具生成文件指纹（SHA-256），便于发现证据记录后来被修改。相同指纹说明文件内容相同，不说明实验方法正确；指纹变化则提醒重新核对旧评分是否仍适用。清单中的命令只是文本，审计器不会执行它们，也不会根据模型输出自动运行 shell。

演示时选择一条命令实际复跑，比较轨迹与预期。模型输出可能不同，重点是契约、预算和证据是否仍满足要求。若要比较改动前后，应保留两个版本的全部结果，而不是覆盖旧失败。

## 动手验收

本课 [lab](../labs/C10-capstone/README.md) 不再增加算法 TODO。你填写本地交接清单并运行 `audit.py`，连接 C07 记录、C08 评测、代码文件与失败分析。它检查材料是否齐全、文件是否改变、来源是否混用；老师仍需核查解释和实际复现，不能把清单完整等同于个人掌握。

| 动作 | 通过所需证据 |
| --- | --- |
| 演示一个任务 | 真实执行或明确标注的模拟轨迹，能解释消息与状态变化 |
| 查看十题比较 | all 与 agent 各十条位置；未运行与待审不隐藏 |
| 分析至少一个失败 | 可定位的失败记录、证据与假设分开、改动或不改的理由 |
| 运行交接审计 | 证据链接和指纹有效，说明配置、预算与复现步骤 |
| 复盘理解 | 用新情形解释限制，能指出尚未验证的能力 |

交接清单通过但所有试验都是模拟时，只得到 `simulation_only`。真实记录完整可得到 `evidence_complete`，仍需解释与复现验收。实验有失败并不自动阻止课程完成：关键是按原目标确认核心功能、识别失败并说明边界；核心功能本身未实现或无法运行时必须记录未完成。

## 从结果选择下一阶段

下一阶段应由最主要的证据缺口决定。若检索漏掉关键段落，先改善分块或检索评测；若资料正确但推断不稳，先检查输出与语义评分；若工具失败频繁，先完善错误处理；只有任务确实需要并发或长时恢复，才进入相关拓展。

新情形：换了一个更强模型后，旧压缩策略使正确率下降。不要因策略来自知名文章就保留它，也不要因模型更强就假定所有旧机制无用。固定其他变量，重新比较带策略和不带策略两种情况，记录变化。这延续了课程最初的原则：用实践检验设计，用证据限制结论。
