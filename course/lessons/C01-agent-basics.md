# C01：Agent 基础与任务定义

本讲介绍控制流、基线选择与验收设计。对应 [课程大纲](../syllabus.md)，基础范围见 [prerequisite.md](../../prerequisite.md)。

## 要解决的问题与验收目标

面对“从少量本地 Markdown 资料中回答问题”的需求，怎样决定采用普通程序、单次模型调用、固定工作流还是 Agent？怎样判断程序完成了任务？

前置知识：知道模型接收输入、生成输出，以及工具由外围程序执行；能阅读简单的函数调用与条件语句。模型 API、具体 SDK 和框架知识在后续实践中补充。

C01 完整验收包括：解释不同方案的控制流、明确任务与权限范围、定义三个可核对的验收问题、保存最简单可运行方案作为后续比较基线。已有个人基础检查时直接衔接，不重复十题。

建议按“明确任务 → 比较控制流 → 选择基线 → 定义验收 → 实现与检查”的顺序学习。可以分段进行，讲解与实践均计入课程预算；完成概念练习不等于通过完整的实现验收。

## 第一段：谁决定下一步

先区分两个观察角度：**数据流（data flow）**描述内容如何传递；**控制流（control flow）**描述下一步执行什么，以及由什么条件或决策触发。

本课采用以下工程区分，不把术语当作所有资料都一致采用的唯一分类：

| 方案 | 资料问答的例子 | 主要步骤如何决定 |
| --- | --- | --- |
| 普通程序 | 按关键词查找资料，直接返回匹配片段。 | 程序定义检索与返回逻辑。 |
| 单次 LLM 调用 | 程序将选定资料和问题一起提交给模型，生成回答。 | 程序安排一次请求；模型生成内容。 |
| 固定工作流（workflow） | 按程序规定先检索、必要时重写查询再检索一次，最后生成回答。 | 主要步骤及分支由程序预先编排。 |
| Agent 循环 | 模型根据问题与工具反馈，选择继续搜索、读取某篇资料或结束回答。 | 模型反复选择下一动作；程序定义可用动作、校验执行并施加运行上限。 |

模型可以生成检索词、选择预设路由或参与评分，这些能力也可以嵌入固定工作流。判断时要检查它对执行过程的控制范围。调用次数多、有工具或有循环，都不足以单独判断系统采用了哪种方式。

以上借用 R003 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 对预设流程与模型动态选择动作的区分；例子及课堂安排是本课程的教学设计。2026-10-23 已核对相关正文；本节不使用其中的具体框架/API 用法。

## 行为预测练习

以下是未运行的 Python 风格伪代码。`search`、`llm_rewrite` 和 `llm_answer` 仅表示职责，尚未接入实现。

```python
def answer_question(question):
    hits = search(question)
    if not hits:
        query = llm_rewrite(question)
        hits = search(query)
    return llm_answer(question, hits)
```

这段程序更接近固定工作流还是 Agent 循环？指出决定再次检索的具体位置，并解释模型在这里能决定什么。

先由学习者预测，再沿调用关系核对。其后才讨论怎样修改控制方式，以及为什么值得修改。

## 第二段：选择基线与定义验收

本段限定任务：针对一个用户问题，程序将三篇短 Markdown 的文件名与全文交给模型，一次生成有依据的回答。输出须标注来源和对应依据；资料不足时说明缺口。资料只读。

基线选择是工程起点，不是效果承诺。“资料能放进窗口”说明输入容量可行，不证明回答正确；参数量也不能单独决定是否必须采用检索。回答、引用、说明缺口是本任务的输出要求，三篇资料不等于三个独立问题。

固定检索流程先筛选证据，可能减少无关输入，也可能遗漏必要片段。它同样可以只调用一次回答模型，因此“调用几次模型”和“如何组织资料”是两个需要分开的设计维度。只读任务也可以采用 Agent；是否写文件不能决定分类。

比较设计：保持模型版本、问题、输出要求与评分口径一致，比较 A“全文 → 回答”与 B“检索 → 回答”。记录必要证据是否进入输入、回答是否符合资料、引用是否支持结论、资料不足时是否编造，以及用量与延迟。必要时在相同预算约束下有限重复；实际结果应通过实验取得。

资料组织与检索缺失的讨论参考 R009 [Introducing Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)，2026-10-23 已选读相关段落；未使用其中的历史模型容量、价格或性能数字作为本项目结论。

### 验收设计练习

练习使用三份虚构的短资料，所需信息如下。它们是供问答系统分析的内容，不代表读者或被测系统已经执行了其中的操作。

| 资料名 | 已知内容 |
| --- | --- |
| rules.md | 只读取提供的资料；回答标注文件名与对应依据；资料不足时说明缺口。 |
| limits.md | 单次任务最多执行 3 次工具调用；每次 search 或 read 各消耗 1 次额度。 |
| trace.md | T01 已执行一次 search 和一次 read，没有其他工具调用，尚未回答用户。 |

学习者设计三个验收问题，填入问题、期望行为和核查依据。留出独立尝试，不预先填写完整答案。

| 类型 | 你提出的问题 | 什么输出算通过 | 应核对哪些资料 |
| --- | --- | --- | --- |
| 单处证据 | 待填写 | 待填写 | 待填写 |
| 组合两份资料 | 待填写 | 待填写 | 待填写 |
| 资料不足 | 待填写 | 待填写 | 需检查全部资料，不能把“未找到”直接等同于事实不存在 |

每条用例应包含“输入问题 → 预期行为 → 核查依据”，并分别检查结论、来源和必要说明。先确定判定口径，再运行模型；不要把预期答案一起传给被测模型。上表是可填写的练习骨架。

用例中的“达到上限”与“超过上限”需分别定义；计算费用既需要适用计费规则，也需要实际计费用量，或直接取得可对应任务的账单。工具调用次数不能直接代表模型调用次数或 token 数。这些是评分规则的一部分，不表示已验证真实 API 的计费行为。

定义用例后，构建最简单的可运行基线：程序读取三篇文件并保留文件名，将全文与单个问题组织为输入，调用一次模型并保存输出，按验收集逐项核对。保存验收集与实际通过验收是两个不同步骤。

### 输入组装练习

可以先实现 `build_messages(question, documents)`：将规则放入 system 消息，将实际文件名、资料正文和问题放入 user 消息。先预览请求，再逐题执行。`documents` 应包含实际资料文本，不能只传本地路径。

API 配置在实际运行前按所选服务的官方资料核对，凭据通过运行环境提供。请求预览成功只说明输入已组装；需要实际运行并核对结果，才能判断基线是否通过。没有模型接口时可以演示模拟流程，但须标明真实模型效果未验证。

## 完成标准

完成本讲时，应能够：

1. 沿着代码指出数据如何传递、下一步由谁决定，解释为什么有循环不一定是 Agent。
2. 明确资料助手的输入、输出、权限范围和资料不足时的行为，说明初版方案的选择依据。
3. 定义三个可核查的问题与评分标准，分别覆盖单处证据、组合资料和资料不足。
4. 保存最简单的可运行基线，记录真实运行或模拟运行的条件与结果，并指出尚未验证的部分。

个人回答、理解证据和实践结果记录在本地学习记录中。教师讲解或阅读讲义不替代独立解释与实践验收。
