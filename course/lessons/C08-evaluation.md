# C08：评测、轨迹与失败分析

C07 可能已经产生几份看起来不错的回答，但“这次读起来顺畅”还不足以比较系统。提示词修改后是否修好了旧错误？是否让另一个任务变差？检索器找错材料，还是模型拿到材料却推断错了？要回答这些问题，需要先定义可重复的任务与判断依据，再保存每一次运行。

本课解决：**怎样把“效果不错”变成可核对、可诊断的证据？** 前置是 C01 的验收问题、C02 的字段校验和 C07 的运行记录。你要扩充为十个小型任务，实现一个分层评分决定，用正确引用但错误结论的反例校准评分器，并比较同条件下的基线与 Agent。

## 把评测拆成几个明确对象

一个**任务（task）**包含输入问题和事前写好的成功标准。例如“判断 T01 是否达到上限”要求结论正确、引用任务记录和额度规则。一次具体运行称为**尝试（trial）**。相同任务运行三次是三个尝试，不能只保留最满意的一次。

**评分器（grader）**检查某个方面，可以是 Python 断言，也可以是人工逐项核查。**轨迹（trace）**保存执行过程，如请求、工具参数、结果与停止原因。**结果（outcome）**是任务真正要交付的东西；本项目是有依据的回答。如果任务改成写文件，结果就需要检查实际文件，而不是只相信“文件已经写好”的自述。[R006](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

这几个对象分开后，一个回答可以同时具有“工具调用成功”“格式合法”“事实错误”三个标签，彼此并不矛盾。评测器应保留这种差异，而不是在打印出 JSON 后就宣布成功。

## 先写规则，再观察输出

本课程提供十个公开案例，覆盖单处证据、多文件组合、资料不足、任务混淆、规则适用范围和达到/超过上限的边界。E01–E07 用于开发；E08–E10 暂留到修改后检查。它们都公开在仓库中，不能称为秘密测试集。如果开发时已经看过并针对其结果调试，就应把它们重新视为开发案例，另准备未用于调试的问题。

题目只进入被测系统，预期答案与评分规则留在评测程序。C07 读取 `tasks.json`，检索器只访问固定资料名单；`C08-expectations.json` 不进入请求或工具目录。这个分离避免模型直接读到答案，也让我们能检查输入是否被污染。

评分不强制唯一文风或工具顺序。T01 “未达到”与“2 小于 3，因此还没到”都可能成立；是否出现某句固定措辞不是核心。与此同时，资料不足不能写成毫无依据的金额，引用也不能只是文件名正确、内容随意编写。

## 分层判断，保留待审状态

本课按以下顺序检查，先发现的阻断项作为分类。分类是定位入口，不自动等同于根因。

| 层次 | 例子 | 判断方法 |
| --- | --- | --- |
| 运行 | 到上限仍没有答案，或接口失败 | 检查记录状态，不把它改为资料不足 |
| 结构 | 缺字段、布尔值变字符串、组合规则冲突 | C02 字段与跨字段检查 |
| 引用 | 文件不存在、引文不在原文中、缺必要来源 | 对照该次资料快照 |
| 可回答性 | 费用资料缺失却声称能计算 | 对照事前定义的任务标签 |
| 语义 | 引文真实但答案推错，或适用对象错误 | 人工根据原文与评分规则判断 |

通过前四层仍不自动通过第五层。没有人工语义判断时，结果是 `pending`。复核文件绑定运行记录的 SHA-256，防止修改答案后误用旧判定；它只保证这份判定对应这份文件，不证明人判断得一定正确。

一个虚构反例是：答案写“T01 已达到上限”，引用却写“共 2 次；上限 3 次”。JSON 合法，引用存在，但 `2 < 3` 与结论冲突。给评分器这条已知错误的记录，检查它是否错误放行。这就是**评分器校准**：不仅测试被测系统，也测试判断工具是否会误报或漏报。

模型评判可以帮助处理大量语言结果，但增加成本，并可能受文风、顺序和自身知识错误影响。本课先用明确规则与少量人工核查建立可信样例，不把再调用一个模型等同于事实验证。[R052](https://arxiv.org/abs/2306.05685v4) 的全文与具体偏差实验尚未在本课精读或复现。

## 数字怎样才不误导

如果十题只运行了七题，其中六题通过，不能写“总成功率 6/7”而隐藏三题未运行。报告应至少列出计划数、通过、失败、待审和未运行。本课模板包含两种方案各十个位置；没有记录的位置保留为 `not_run`。

模拟响应和真实模型结果分开统计。模拟全部通过只说明程序符合这些构造输入的预期，不代表真实模型会正确选择工具。耗时和用量也按运行来源与方案分组，不能把本地模拟的毫秒级延迟与真实 API 延迟混成均值。

多次重复能观察波动，但应预先约定次数，保留所有尝试，并标明指标。第一次正确、第二次错误说明稳定性有问题；不能挑第一次作为唯一“代表”。本课用小样本诊断，不给出普遍可靠性结论。环境配置、工具超时或资源不足也能改变结果，应与答案推理错误分别分析。[R016](https://www.anthropic.com/research/infrastructure-noise)

## 动手实验

按 [实验说明](../labs/C08-evaluation/README.md) 实现 `decide`。教师代码负责读取日志、解析答案、检查原文和汇总；你决定各层检查如何导向 `pass`、`fail`、`pending`。先运行四类校准测试，再用 C07 已有记录填写本地评测清单。

| 动作 | 观察什么 |
| --- | --- |
| 给评分器格式错误和伪引文 | 是否分别归类，而不是抛弃这次运行 |
| 给正确引文、错误推论 | 自动检查通过后是否待审，负面人工复核后是否失败 |
| 保留几条未运行任务 | 汇总是否仍显示未完成数量 |
| 比较 all 与 agent | 同题对照结果、证据缺失位置和实际请求量 |

十题是评测集规模，不意味着默认一次性付费运行所有方案。先整理和评分已有结果；如果真实运行时间或预算不足，保留未运行项并协商，不用模拟结果填补。命令不会自动调用模型，也不会在失败时偷偷重试。

## 复盘与下一课

选择一次失败，沿“最终结论 → 模型实际收到的证据 → 工具结果 → 请求参数”反向查找。若证据根本不在输入中，先解释为什么没选中；若证据已在输入中，分析是否读错对象或推断错误；若根本没有正常响应，先处理运行层问题。

新情形：模型在十题中答对九题，唯一失败来自读取超时。它仍是这次端到端任务的失败，但修复方向可能是工具故障处理。C09 继续研究怎样增加有界重试，同时避免把无效参数、权限拒绝或错误结论一律重试。

## 深入阅读

- **15–20 分钟：R006 的评分器与从零构建评测部分。** 用自己的案例解释为什么只评分最终文字或只检查工具成功都可能漏错。
- **10–15 分钟：R036，[τ-bench v1](https://arxiv.org/abs/2406.12045v1)，Shunyu Yao 等，2024-06-17。** 本次复核摘要与元数据，关注用最终环境状态检验结果的思路；全文留给 [论文路线](../papers/index.md)，本课没有模拟用户或数据库任务复现。
- **10 分钟：[讲义试读办法](../evals/lesson-readthrough.md)。** 同样检查“评分是否反映真正目标”：复述术语不等于能解释新的失败案例。真人试读和作者自检是不同证据。
