# C02：模型交互与结构化输出

本讲承接 [C01 单次调用基线](C01-agent-basics.md)，学习怎样把模型返回的文本变成可以检查的业务数据。对应 [课程大纲](../syllabus.md)，沿用三份虚构资料，不引入工具调用或 Agent 循环。

## 要解决的问题与验收目标

请求成功、JSON 能解析、字段符合约定、答案有依据，是四种不同的判断。本课的目标是沿代码区分它们，并在失败时保留诊断信息。

前置知识：Python 字符串、列表、字典、异常；知道 C01 的输入和评分要求。教师提供文件读取、HTTP 传输、字段检查和记录骨架；学习者填写消息要求与跨字段校验，不要求独立重写传输层。

建议 60 分钟：5 分钟回顾、15 分钟原理与示例、30 分钟实现和运行、10 分钟验收。缓存的详细数学与推理引擎实现属于可选深入内容。环境或实验超时，应调整课内范围，不默认增加必修作业。

完成标准：

1. 解释 system、user、assistant 消息及多轮历史如何进入下一次请求。
2. 区分输入、输出、缓存命中与上下文预算，解释生成长度不足的影响。
3. 完成 JSON 输出提示词和跨字段校验，运行并检查三种资料问答任务；没有真实接口时注明端到端效果未验证。
4. 分析一个结构合法但内容不符合要求的结果，说明现有检查能保证什么、仍不能保证什么。

## 第一段：消息与上下文由程序组织

在本课使用的 Chat Completions 请求中，system 放应用要求，user 放实际资料和问题，assistant 表示模型回答。模型收到的是消息里的内容，不能仅凭本地路径读取文件。角色标签表达消息来源，不是程序执行权限或事实正确性的保证。

C01 的三题分别是独立请求，每题只有 system 和本题 user。前一题的回答不会因为共用 API key 就自动成为后一题的输入。当前 DeepSeek `/chat/completions` 的多轮对话需要显式传入历史，见 [官方多轮说明](https://api-docs.deepseek.com/guides/multi_round_chat/)。

以下是未执行的消息排列示意，变量为占位符：

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": documents_and_first_question},
    {"role": "assistant", "content": previous_answer_text},
    {"role": "user", "content": followup_question},
]
```

这是发送追问时的列表；收到新回答后，程序才追加新的 assistant 消息。上一轮输出可以在下一轮成为输入。历史回答即使长得像 JSON，放在这里的 content 仍是 JSON 文本字符串。

检查问题：如果只发送“那还剩几次？”，省略资料与前轮问答，模型有没有足够的本次输入来核对任务状态？答得碰巧正确与依据充分有什么区别？

## 第二段：两层 JSON 与业务数据约定

接口的外层响应是 JSON，不代表其中的回答字符串也能作为 JSON 解析。下面是职责示意，不是完整可执行程序：

```python
result = json.load(response)  # 外层 API 响应，通常得到 dict
text = result["choices"][0]["message"]["content"]  # 本课检查为非空 str
data = json.loads(text)  # 业务内容；可能抛出 JSONDecodeError
```

JSON 使用 `true`、`false`、`null`；解析为 Python 后分别得到 `True`、`False`、`None`。`True|False`、`str|None` 和注释可以用于解释类型，但不是合法 JSON 示例。解析规则与类型映射见 [Python json 文档](https://docs.python.org/3.12/library/json.html)。

本课定义如下业务契约；这是课程设计，不是 API 自带的字段保证：

| 字段 | 约定 |
| --- | --- |
| answerable | 布尔值，表示给定资料是否足以支持回答；允许有依据的跨文档推导。 |
| answer | 可回答时为非空非纯空白字符串；不可回答时为 null。 |
| citations | 对象数组，每项含非空非纯空白的 file、quote；quote 是对应文件的原文。可回答时至少一项。 |
| missing_information | 字符串数组；可回答时为空，不可回答时非空；每项具体说明一个缺口，且非空非纯空白。 |

不可回答时，有相关资料就引用已有事实，说明资料目前覆盖了什么；没有相关内容时允许空 citations，不为缺失信息伪造引文。结构校验只能允许或拒绝空数组，是否遗漏相关依据要结合资料判断。沿用的 E03 有相关任务记录，因此仍适用 [原有来源要求](../evals/C01-baseline-cases.md#c01-e03资料不足)。

实现分成三步：

1. **解析**：文本能否交给 `json.loads`。
2. **字段检查**：必需字段是否存在，类型和每项的非空要求是否符合约定。
3. **跨字段一致性**：answerable、answer、missing_information 的组合是否成立。

练习：在字段与类型已检查的前提下，实现 `validate_consistency(data)`。违反组合规则抛出 ValueError，通过返回 None。准备可回答与不可回答的正常输入，以及空白答案、错误组合和空白缺口条目，分别说明应由哪一层拒绝。不要把答案的字面值写成固定测试通过条件。

当前实验骨架检查必需字段，但不拒绝额外字段，也不实现完整的严格 JSON Schema 校验。提示词写“恰好四个字段”不会自动增加程序检查；应明确所声称的保证与实际代码是否一致。

## 第三段：提示词、JSON 模式与实际输出

提示词应明确四字段、两种回答情形、所有情形下的引用要求，以及一个不包含验收答案的合法 JSON 示例。把实际资料与问题放进 user，评分参考留在模型输入之外。

实验使用 `response_format={"type": "json_object"}`，提示词同时写明 JSON 和期望格式。DeepSeek 的 [JSON Output 说明](https://api-docs.deepseek.com/guides/json_mode/) 还提醒空内容和输出截断的可能性。此模式不替代本课程的字段、组合关系与事实核查；不把它与严格按指定 Schema 生成混为一谈。

字段失败时先核对提示词与程序契约。例如，提示词要求 missing_information 为 null，而校验器要求数组，是应用自身的不一致，不能直接归因为模型能力不足。改变提示词、参数或模型时，保留旧结果并固定其他条件，才能分析变化。

## 第四段：token、生成上限与上下文预算

Token 是分词器处理后的模型输入/输出单位，不等同于字符或单词；精确数量取决于对应分词器与消息编码。已完成请求可查看 usage，不能用字符数冒充精确 token 数。

本课关闭 thinking，按 [Chat Completions 参数说明](https://api-docs.deepseek.com/api/create-chat-completion/) 区分以下量；换模型、模式或接口时重新核对定义：

| 名称 | 含义 |
| --- | --- |
| prompt_tokens | 本次输入总量，包含缓存命中和未命中的输入。 |
| completion_tokens | 本次实际生成的 token 数。 |
| total_tokens | 本次输入与生成数量之和。 |
| max_tokens | 请求设置的生成数量上限，不是输入与输出合计，也不是必须用满的数量。 |
| 上下文长度约束 | 模型与服务支持的序列范围；本课预算例子按输入和生成合计检查。 |

教学假设：某服务允许输入与输出合计最多 4096 tokens，本次输入 3900，其中缓存命中 3000，希望预留输出 512。说明这个预算是否成立，以及为什么缓存命中不能从输入长度中扣除。这些是假想规格，不是 DeepSeek 的实际容量。

`max_tokens` 过小可能使回答在 JSON 写完前结束。先检查 finish_reason 与原始记录，再判断是否需要调整输出预算、精简输出或减少输入；仅重试相同请求可能重复同一失败。输出上限不等于整个请求的费用上限，费用未知时明确记录未知。

### KV cache、prefill 与 decode

以标准因果自注意力为例，各层从 token 表示计算 Q、K、V。当前 Q 与各位置 K 计算权重，按权重汇总 V；已有位置不会读取未来 token，因此在模型和前缀一致时，已有 K/V 可以复用。

KV cache 保存各层已处理前缀的中间结果。新位置仍计算自己的 Q/K/V，并使用旧 K/V；旧内容继续参与注意力，逻辑上下文长度没有缩短。缓存不是一份自动加入请求的聊天历史，也不是模型参数更新。

- **预填充（prefill）**：处理输入前缀，建立缓存并产生第一个输出 token 的预测。
- **解码（decode）**：处理刚生成的 token，复用历史缓存，预测下一个 token。已处理的输出 token 的 K/V 也会供后续步骤复用。
- **跨请求前缀复用**：下一轮显式传入历史后，前一轮的输出成为新的输入。服务若保留兼容缓存且实际前缀匹配，就有机会减少新请求的 prefill 工作；新的回答仍需生成，命中并非必然。

因此，“普通 KV cache 减少 decode 中重复处理历史的工作”和“跨请求前缀缓存主要减少 prefill 工作”可以同时成立，二者比较的基线不同。具体压缩、共享或滑动窗口实现不在本课必修范围；不能从 API 的缓存 token 数推断精确显存布局或哪些文字恰好命中。

## 第五段：结构合格之后还要检查什么

考虑一份人工构造的业务对象：答案说“最多 30 次”，引文却是 limits.md 的“单次任务最多执行 3 次工具调用。”，其他字段符合约定。先预测：结构校验会发现问题吗？再检查“引文确实存在”是否足以证明它支持答案。

这是课堂反例，不是模型真实错误率样本。文件存在、引文匹配、引文支持结论、回答完整满足任务要求，需要分别核查。确定性的文件名与片段检查可以写成程序；开放式语义和引用遗漏仍需有评分规则的人工或额外评测，不能直接由格式通过推出。

另一个人工示例是 finish_reason 为 length，content 只剩未完成的 JSON 前缀。外层响应可能已经成功解析，但业务回答未正常生成。本课程序先保存可解析的外层响应，再检查结束状态；状态不符合要求时返回非零值，不把片段自动补成“answerable=false”。生成失败并不能证明资料不足。

排查时区分执行状态、数据契约和资料内容：

| 检查层 | 失败时保留与核对的依据 | 本课处理范围 |
| --- | --- | --- |
| HTTP、网络与外层响应 | 错误类型、状态码及实际请求配置。超时不能证明服务端未执行。 | 不自动重试；外层无法解析时，当前骨架没有完整的原始字节归档。 |
| 结束原因与回答内容 | 已保存响应中的 finish_reason、content 和 usage。 | 异常结束或空内容不进入业务成功路径。 |
| 业务 JSON 与数据契约 | 原始 content、字段类型和组合、提示词要求。 | 解析与约定失败返回非零值，原始响应保留。 |
| 来源与任务结果 | 给定资料、引用片段、问题与预先确定的评分规则。 | 当前由人工核查；结构通过不等于本层通过。 |

再调用一个模型评判称为 LLM-as-a-judge。它也可能误判，加入前应以人工判定样例核对评判能力。额外推理有开销，是否降低整体评测成本需连同人工工作量与误判代价一起比较；本课不要求实现自动评判器。

## 实验与收尾验收

进入 [C02 实验](../labs/C02-structured-output/README.md)，使用消息构造和一致性校验骨架，按 [C02 验收参考](../evals/C02-structured-output-cases.md) 检查。实验沿用 [C01 的问题与资料](../evals/C01-baseline-cases.md)，将自然语言输出改为四字段 JSON。先在被忽略的本地副本作答，预览输入，再逐题运行、分别评估结构与内容。没有真实接口时可以演示程序控制流，但必须注明真实模型行为未验证。

至少分析一个格式或事实不满足要求的案例：若三题都通过，可使用上文明确标注的人工反例检查校验边界，不必反复调用模型寻找失败。结构与业务评分分别记录；观察并解释失败属于课程目标，不要求把所有样例调试到通过才结课。

最后用 5–8 行伪代码解释“收到响应 → 各层检查 → 可接受的业务结果”，标明现有程序与人工核查的分工，并分别定位 length 截断与资料不足时遗漏引用的失败。保留原始结果；修改后的回归须使用同一版本，不能拼接不同版本的成绩。

个人实现、原始回答、成绩和学习诊断只保存在 Git 忽略的本地记录中。课堂模拟、真实请求与底层机制说明分别记录；没有独立实现的能力不由教师演示替代认定。下一课 C03 将把结构化输出连接到工具参数校验与实际执行。
