# C05：上下文、运行状态与持久记录

C04 的循环已经可以把阅读结果送回模型。现在把同一个系统用于更长的资料：每读一次，下一次请求就多一段原文。虽然运行只有几步，输入仍可能很长；如果每次都带上所有历史，早先的大段结果会被反复发送。我们需要决定哪些信息进入下一次请求，同时保留能够核查发生过什么的原始记录。

本课解决的问题是：**缩短模型输入时，怎样知道自己没有把回答所需的信息一起删掉？** 前置知识是 C04 的消息配对、计数器和停止状态，以及 Python 字典、列表和深复制。完成后，你要能区分三种信息存放位置，实现一种可检验的裁剪策略，并解释一个“输入更短，但证据消失”的失败。

## 从一次阅读说起：信息到底在哪里

假设程序调用 `read_document("recovery.md")`，读到恢复编号 `QH-742`。这个编号可能同时出现在原文件、运行日志、内存中的历史列表和下一次 API 请求中。这些位置有关联，却不意味着模型都能直接访问。

**上下文（context）**是这次模型请求实际提供的信息。对于本课程使用的显式消息接口，程序把哪些消息放入 `messages`，这些消息才成为此次输入。历史文件仍在磁盘上，却没有被读取并送入请求，模型就不能仅凭“文件还在”获得其中编号。

**运行状态（runtime state）**是程序用来继续执行的事实，例如已经尝试几次模型请求、用了多少工具额度、当前状态是否为 `max_steps`。这些值由程序更新。即使模型输入删掉了两段旧工具结果，也不应把计数器减去两次；动作已经发生，输入整理不能撤销动作或恢复额度。

**持久记录（persistent record）**是进程退出后仍保存的内容，例如 `.local/` 中的 JSON 轨迹。它使我们以后能检查原始工具输出，却不会自动成为下一次模型的记忆。需要恢复信息时，仍要有明确的读取、选择和注入路径。保存日志也不等于具备任务恢复功能：恢复还要判断哪些动作已经执行、是否允许重放，以及状态如何保持一致。

| 位置 | 这个例子里保存什么 | 谁负责使用 |
| --- | --- | --- |
| 模型本次输入 | 问题、规则、选中的工具结果 | 模型据此生成下一步 |
| 程序状态 | 已用次数、停止原因 | 程序检查运行上限 |
| 文件或日志 | 完整原文、请求和响应快照 | 程序在需要时重新读取；人可以事后核查 |

这个区分解释了一个常见误解：“我把工具结果从历史里删了，所以这次调用也不占预算了。”成立的部分是下一次输入确实可以变短；错误在于把输入内容和已发生的执行次数混成同一个状态。反例是请求已计费后删除本地日志，服务端也不会因此撤销请求。

## 从原始历史生成本次输入

最容易检查的做法是保留原始历史，再从它生成一份要发送的副本。我们把这个步骤称为**投影（projection）**：它不是训练模型，只是从已有记录构造下一次输入。

```text
完整运行历史 ──复制并选择内容──→ 本次 messages ──→ 模型
     │
     └── 原始日志保留，用于核对与重新获取证据

程序计数器独立保留，不随 messages 的长短变化
```

Python 的浅复制只复制外层列表，内部字典仍可能共享。例如 `selected = messages[:]` 后直接修改 `selected[-1]["content"]`，可能连原始历史也改掉。实验使用深复制，是为了让“模型看到了什么”和“工具原来返回了什么”都能分别核查。

还要保留 C03 的协议关系：assistant 提出的工具调用及其对应的 tool 消息具有同一个调用 ID。随手删除一条消息，可能留下没有请求的结果，或者没有结果的请求。本课不删除消息，只在副本里改变成功工具结果的正文，保留调用、ID、文件名及错误信息。这样可以把信息选择的影响和协议损坏分开观察。

## 一个可以失败的裁剪策略

本课选择首尾裁剪作为比较对象：正文超过上限时，保留前半额度和后半额度，中间加“内容已裁剪”的标记。这里用字符数，目的是让代码简单且能精确复核；它不是 token 估算器，更不是整个上下文窗口的保护器。

例如正文为 `abcMIDDLExyz`，保留额度为 6，发送的内容变成 `abc`、裁剪标记和 `xyz`。`original_chars=12` 告诉读者原文有多长，`truncated=true` 表示当前正文不完整。标记本身也占输入，因此短小工具输出加上额外字段反而可能更长；没有超过阈值时应直接返回内容副本。

为什么不直接取前 6 个字符？两种方法都能减少输入，但保留的信息不同。本课使用首尾不是因为它普遍更好，而是因为它能产生一个清楚的反例：把恢复编号放在长原文中间，首尾仍在，唯一支持答案的证据却不在了。必须同时测输入量与证据保留，才能评价策略。

摘要（summarization）是另一种方法：让模型把原文改写为较短表述。它可能保留更多相关信息，也增加一次生成、成本以及遗漏或改写错误的机会。摘要中出现“编号是 QH-742”不等于这句话就是原始引用；需要保留原文位置并在必要时回读。本课不追加摘要模型调用。

## 怎样解释实验结果

实验 fixture 是人工构造的 `recovery.md` 工具结果。完整输入含 `QH-742`，首尾裁剪后不含。脚本报告两份序列化消息的字符数，以及编号是否仍在。这个检测只证明特定字符串是否保留，不是对任意任务的语义评分，也不是模型回答。

如果有模型接口，可显式发送完整与裁剪输入各一次。预测是完整输入有足够证据，而裁剪输入应说明缺少编号。实际模型也可能猜出一个编号、误答、忽略证据或拒答；无论碰巧答对与否，都要检查引用是否存在于它收到的内容中。不能把猜中的结果当作裁剪成功。

费用也要分层理解：字符数减少只是输入规模指标；实际 token 用量以响应的 `usage` 为准。缓存命中的输入仍属于逻辑上下文，只是某些计算或计费可以复用。两次请求的缓存、输出长度和服务延迟可能不同，因此单次对照不能证明费用或速度稳定改善。精确金额未知时保留为空，不用字符数冒充账单。

## 动手实验

打开 [实验说明](../labs/C05-context/README.md)，复制骨架后实现 `trim_result`。投影、消息配对和日志由教师代码提供。本课不重写 C04 循环，也不要求实现持久记忆系统。

| 动作 | 事前预测 | 运行后检查 |
| --- | --- | --- |
| 处理短正文及错误结果 | 不改变正文和错误 | 内容相等，但可独立修改副本 |
| 裁剪长正文 | 首尾保留，中间消失 | 标记、原长、文件名正确 |
| 投影完整消息 | ID 与角色顺序不变 | 原始历史仍含编号，副本不含 |
| 比较完整与裁剪输入 | 输入规模变化，证据可能丢失 | 字符数、证据、真实输出分别记录 |

分层提示：先只处理正文超长这一分支；再加入副本与元数据；最后检查奇数额度和没有超限的边界。失败时先查看原始与投影结果是否不同于预期，再考虑模型行为，避免把确定性的裁剪错误归因于模型。

## 复盘与下一课

用一个新情形检查理解：工具结果被裁剪后，下一轮模型要求重新读取同一文件，程序应不应该退还上一次额度？解释信息恢复与执行次数的区别，并指出现有投影器可能再次裁掉刚读回的证据。解决办法需要调整选择策略，而不是无界重复读取。

验收见 [C05 核查](../evals/C05-context-cases.md)。能展示裁剪反例并解释其原因，就已经得到有价值的工程结论；无需把首尾裁剪包装为最优方案。C06 接着研究如何在发送前找到相关片段，让“保留什么”逐步由固定位置转向任务需要。
